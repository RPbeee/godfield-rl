# 魔法反射4種と奇跡の来歴 v16

`legacy-magic-reflection-subset-v16` は魔法反射40/171/174/178を追加する限定profile。
CLIの `magic-reflection` と `gz_*` は既存拡張も有効にし、185種・旧重み合計375で動く。
旧非公式エミュレーターを参考にしており、現行公式との完全一致は確認していない。

[処理順の調査](legacy-magic-reflection-rules.md)、[台帳・出典・hash](../data/legacy-magic-reflection-v1/README.md)、
[前段の所持金反撃profile](legacy-money-counter-profile.md)を参照。
既存15台帳を変更せず、追加4種を含むプール内で旧重みを正規化する。公式の配布率とは扱わない。

## 神器と役割

| 旧ID | 種別 | ATK / 追加ATK / DEF | 防御の特殊効果 | 旧価格 / 重み |
| --- | --- | --- | --- | --- |
| 40 | 武器 | 10 / 0 / 0 | 魔法反射 | 15 / 1 |
| 171 | 防具 | 0 / 0 / 9 | 魔法反射 | 10 / 1 |
| 174 | 防具 | 0 / 0 / 10 | 魔法反射 | 10 / 1 |
| 178 | 防具 | 0 / 0 / 11 | 魔法反射 | 10 / 1 |

全4種とも無属性・MP費用0・保持化なし・攻撃付随効果なし。
40は通常のATK10武器として使い、通常boostを追加できるが、40自身は追加ATKには使えず捨てられない。
3防具は捨てられ、MAGIC以外の攻撃には通常DEFを使う。counterへの通常防御も同じ。
MAGICを受けて選択した場合は必ず魔法反射が発火し、自身の印字DEFを使う前に処理を終える。

## 応答と反射

MAGICへの4種の使用は `defend.base` に指定する。普通防具用の `slots` へ入れて
反射を任意に省略する行動は拒否する。最初に発火した特殊応答より後の未使用選択は、従来の意味的行動と同様に省略する。
複数の魔法反射神器を同じ行動で消費する表現にはしない。
MAGIC以外では3防具を `slots` へ指定でき、40は普通防御には使えない。

反射は現在のsourceとtargetを交換し、新しい対象へ応答を求める。
全属性・命中済みの確率奇跡・闇攻撃に加え、回復216や所持金220の奇跡も返す。
武器用20/39や魔法跳ね返し210とは別の条件を使い、PROTECTOR由来のcounterは反射しない。
通常の自己対象奇跡は即解決するため、反射を選ぶ応答はない。

前置した普通防具は消費され、配布予定を増やす。病気など、既にプレイヤーへ適用した副作用も残る。
一方、反射で返す威力は元payloadの値で、前置DEFによる減算や反射防具自身のDEFを差し引かない。
195は元の効果そのものの属性を書き換えるため、反射後も無属性化が残る。
MAGICの特殊応答では前置防具の属性適合を要求しない。通常防御だけを選ぶ場合は属性適合を検証する。
Gloryは既存profileと同じ単枚制限を適用し、反射神器も1枚に数える。

反射で奇跡ID・威力・効果・元の保持使用flag・命中記録を維持する。
命中抽選を再度行わず、MPを支払い直したり反射者の保持奇跡へ追加したりしない。
元の通常手番ownerと現在sourceを混同しない。最終的に解決した対象へ回復・所持金・Glory・闇の効果を適用する。
反射と210の跳ね返しを交互に使う連鎖も、最終解決まで補充を待つ。
前置counterは消費されるが、特殊応答のため反撃を予約しない。

## 配布予定・復元

`Config::magic_reflection` はデフォルトfalseで、reflectionとmiraclesを必要とする。
防御奇跡や病気などの他拡張は、それぞれの依存関係に従い個別に選べる。

保持castから始めた反射連鎖では、手札を消費しない元castの配布予定を `retained_deals` として区別する。
この追跡をdefensive_miraclesまたはmagic_reflectionが有効な場合に使う。
防御奇跡が無効なら保持由来の予定は1座席につき最大1で、通常castと手札消費を混同しない。
両者16枚の反射神器と元保持castの組合せでは32回の反射・33回の配布抽選が起こり得る。
満杯時も余分な抽選を消費し、実際の手札容量は16を保つ。

防御奇跡も有効なら、保持応答のMP費用に基づく既存の保守上限20を使う。
反射神器はMPを補給しない。193のMP回復は元MAGIC連鎖の終了後であるため、この証明を崩さない。
反応回数32という上限は置かず、手札とMPによる資源制約に従う。

Snapshot共通versionは37。同じビルド・Config内のfixture用で、旧形式を自動移行する永続checkpointではない。
新しい反射IDの来歴・MAGIC型・元ownerの保持・奇跡量・命中記録・手番順・配布予算・反射回数を検証する。
Heaven前置の暫定HP0と項目終了時の死亡確定を区別し、反射返しで回復が戻れば項目終了前に救済される経路を保つ。

## 観測とAPI

共通観測の追加部分と新しい順序付き行動は[HP吸収v28](legacy-hp-absorption-profile.md)を参照。旧ABIの幅・行動形式は維持する。

共通C++観測は1368次元、gz出力は先頭696次元。v16では末尾672特徴が0。gyは先頭679、gx以前も従来の幅を維持する。
既存の反応記録229〜235で反射ID・種類・source/targetを表す。

| 位置 | 内容 |
| --- | --- |
| 679 | magic_reflection有効なら1 |
| 680〜695 | 自分の各手札が40/171/174/178なら1/2/3/4を4で割る。その他0 |

追加17特徴は旧profileでは0。相手の未使用手札・完全な保持数・未来の抽選値・乱数状態は含めない。
既存の量や反応回数の正規化には1を超えるものがあり、全特徴が0〜1とは仮定しない。

新C ABI [magic_reflection_c_api.h](../include/godfield/magic_reflection_c_api.h) は `gz_*` version16。
行動はgx/gyと同じ16byte、mask幅11、手札容量16を維持する。
魔法反射候補は既存のreaction_slotsへ入れ、MAGICへ必ず発火するカードは普通防具候補から除外する。
maskは構成要素なので、Glory・195・counter順序などを含む行動を `legal()` で検証する。
StepResultの `magic_reflected` と汎用 `reflected` がtrueになる。魔法反射は武器反射のベンチ統計と分ける。

[Pythonラッパー](../python/magic_reflection_env.py)では `MagicReflectionBatchEnv` を使う。

```sh
python3 python/magic_reflection_env.py
./build/godfield_legacy_bench 100000 1 42 magic-reflection
./build/godfield_legacy_bench 100000 4 42 magic-reflection
```

バッチは全active行の事前検証で原子的に拒否する。終了行は固定・報酬0で不正手を無視し、自動resetしない。
報酬は固定座席順。Pythonの返却バッファーは再使用するので履歴へ保存するときはコピーする。
同一ハンドルの同時操作はしない。既存gl〜gkは6byte、gx/gyは16byteで各観測幅も変更しない。

霧188は[表示秘匿の調査](legacy-fog-rules.md)で一次資料の未確定点を残し、配布対象に追加しない。
万能反射196は[後段v17](legacy-any-reflection-profile.md)で扱う。幻覚189、追加魔法・忘却・守護神・蘇生・死亡時効果・終末・複数人戦、
旧版Pythonとの動的差分実行と現行公式照合、学習器・学習済みモデルは未対応。衝突C01〜C05も残す。

## 検証結果（2026-10-31）

通常CTest49件、ASan/UBSan33件、16種類のPython suite計141テストが通過。
4種の兼用役割とMAGICへの強制発火、prefixの不正選択、raw効果・195・Glory・命中来歴、
回復/所持金の対象反転、Heavenの暫定HP0からの回復、COUNTERへの型制約、旧ABI出力境界を検証した。
最小Configで32反射・配布予定17・33抽選、防御奇跡との40反応・41抽選、1000試合replayも確認した。

全機能有効・10万試合・seed42・意思決定上限512で、1/4スレッドの全統計とchecksumが一致した。

魔法反射を武器反射や新しい奇跡使用へ重ねて数えない。
前置防具の減算が破棄された特殊応答を、実際の属性ダメージ軽減として集計しない。
checksum v16は反射回数・反射ID・元奇跡payloadとsource/targetの履歴を含める。
旧15profileのchecksum式を維持し、各10万試合で意思決定数・勝敗・draw・打ち切り・checksumが以前と一致した。
ASan/UBSanのベンチ1万試合でもReleaseの全統計とchecksumが一致した。
速度出力は行動生成・合法性検証・遷移・統計・resetを含み、観測転送・モデル推論を含まない。
