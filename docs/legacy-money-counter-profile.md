# 所持金反撃と不足額の支払い v15

`legacy-money-counter-subset-v15` は所持金反撃194を追加する限定profile。
CLIの `money-counter` と `gy_*` は既存拡張も有効にし、181種・旧重み合計371で動く。
旧非公式エミュレーターの処理順を参考にしており、現行公式との完全一致は確認していない。

[処理順の調査](legacy-money-counter-rules.md)、[台帳・出典・hash](../data/legacy-money-counter-v1/README.md)、
[混合反撃の順序とAPI](legacy-counter-extensions-profile.md)を参照。
既存14台帳を変更せず、追加1種を含むプール内で旧重みを正規化する。公式の配布率とは扱わない。

## 194の予約と解決

| 旧ID | 種別 / 属性 | 通常DEF / MP | 予約額 | 対象 | 旧価格 / 重み |
| --- | --- | --- | --- | --- | --- |
| 194 | COUNTER防具 / 無属性 | 0 / 0 | 普通防御後のraw残余r | 現在のincoming source | 10 / 1 |

194は消費型防具で、保持奇跡・攻撃武器にはしない。通常手番では使用できず、捨てることはできる。
既存の反撃と同じく、元の攻撃がdamage、残余r>0、特殊応答なしの場合だけ予約する。
他の防具と合成し、通常防御・病気・195を処理した後の共通残余rを使う。倍率は1。

起動時に相手の応答を待ち、以下の順序で解決する。

1. counter元へ予約額rを所持金として加算し、上限99で止める。
2. 対象へrの全額を請求する。所持金から払い、不足分をMP、さらにHPから払う。
3. HPは0で止め、項目終了時に死亡を確定する。対象が実際に支払えた額で元への加算を減らさない。

例えば元の所持金20、対象の所持金3・MP4・HP40、請求額10なら、
元の所持金30、対象は所持金0・MP0・HP37となる。
元の所持金が99に達していても対象への請求を減らさず、対象の資源が全て足りなくても元へ予約額を先に加算する。
これは実際に移動できた所持金だけを渡す一般的な送金処理とは異なる旧版の効果。

**194に対する普通DEFは請求額を減らさない。** 195は属性だけを消し、請求を打ち消さない。
防御時の病気など、選択した防具の効果・消費・配布予定は通常どおり処理する。
194はATKでもMAGICでもないため、20/39・210・215を使えず、支払いでHPが減っても新しい反撃を予約しない。
他のcounterを前置選択すれば消費されるが、非damageなので発動しない。

sourceが死亡済みでも予約は実行し、その死者へ所持金を加算する。これで復活することはない。
targetが死亡済みなら項目をskipし、元への加算も対象の支払いも行わない。
194の支払いで死亡した相手を後続項目が狙う場合も、既存の死亡target処理を使う。
後続187は命中処理を行ってからskipするが、非公開のhit/missを観測へ出さない。
両者死亡は学習規約としてwinner=-1・報酬0のdrawにする。

混合反撃の順序はv14の指定を継承する。
例えば194を先に解決するか、先行190で相手を死亡させて194をskipするかにより、所持金も変わり得る。
全キュー終了後に元turn_ownerの病気tick・生存者への補充・勝敗を処理する。

## 状態・観測・互換性

`Config::money_counter` はデフォルトfalseで、counter_extensionsを必要とする。
194だけを旧v13の順序なしAPIへ混ぜず、既存の反撃5種との順序を指定できる構成にする。
他の既存拡張はそれぞれの依存関係に従い個別に選べる。

`Effect::absorb_money` は既存enum末尾の7。既存money効果は対象への単純加算のまま維持する。
予約額はint64の正値で、既存の生成数に応じた威力上限を検証する。
所持金・MP・HPの支払いには64bitの残額を使い、各資源の実減少量は0〜99に収める。
キュー32枠、カード消費予算、source/target/来歴、保持奇跡の配布上限20は維持する。

Snapshot共通versionは35。同じビルド・Config内のfixture用で、旧形式を自動移行する永続checkpointではない。
194/absorb_money/NE/倍率1・正額・非自己対象・付随効果なしの整合を検査する。
無効なConfigへ194を復元・配布する場合や、武器・MAGICへ偽装した項目は拒否する。

共通C++観測は1317次元、gy出力は先頭679次元。v15では末尾638特徴が0。既存gxは先頭661、gk以前も従来の幅を維持する。
既存counter候補maskと自分のcounter手札特徴394〜409は194も認識する。

| 位置 | 内容 |
| --- | --- |
| 661 | money_counter有効なら1 |
| 662〜677 | 自分の各手札位置が194なら1 |
| 678 | 未解決項目がabsorb_moneyなら1 |

公開済みqueueの種類は既存v14特徴のEffect enum/6で区別でき、194では7/6になる。
量の正規化も含め、全観測が0〜1であるとは仮定しない。
追加18特徴は旧profileでは0。相手の未使用手札、乱数状態、未来の抽選や非公開の命中結果は含めない。

StepResultはcounter_money_absorptionsと、実際のcounter_money_gained/lost・counter_mp_lost・counter_hp_lostを追加する。
加算上限や対象の資源不足により、元の実増加と対象の実支払いは一致しない場合がある。
raw予約額を実際の所持金移動として集計しない。HP支払いと病気tickの損失も区別する。

## APIと実行

新C ABI [money_counter_c_api.h](../include/godfield/money_counter_c_api.h) は `gy_*` version15。
行動は順序付き16byteで、gxと同じkind/base/slots/target/count/4bit列を使う。
194もcounter_orderへ消費前の手札slot番号で列挙する。mask幅11、手札容量16、固定座席報酬を維持する。
候補maskには組合せ条件があるため、構成した行動を `legal()` で検証する。

[Pythonラッパー](../python/money_counter_env.py)では `MoneyCounterBatchEnv` を使う。

```sh
python3 python/money_counter_env.py
./build/godfield_legacy_bench 100000 1 42 money-counter
./build/godfield_legacy_bench 100000 4 42 money-counter
```

バッチは全active行を検証してから更新し、不正手があれば全体を原子的に拒否する。
終了行は固定・報酬0・不正手を無視し、自動resetしない。
Pythonの返却バッファーは再使用するので、replayへ保存するときはコピーする。同一ハンドルの同時操作はしない。
既存gl〜gkは6byte、gxは16byteのままで、各ABIの観測幅を変更しない。

188霧・189幻覚、万能反射・追加魔法・忘却・守護神・蘇生・死亡時効果・終末・複数人戦、
旧版Pythonとの動的差分実行・現行公式照合、学習器・学習済みモデルは未対応。資料間衝突C01〜C05も残す。

## 検証結果（2026-10-31）

通常CTest46件、ASan/UBSan31件、15種類のPython suite計129テストが通過。
入金上限・所持金/MP/HPの支払境界、普通DEF/195の非減額、死者source入金とtarget skip、
非damage請求による両死draw、Heaven前置の暫定HP0、混合順序・非公開命中、自然raw255・int64上限、
variant復元と旧ABI出力境界、秘匿観測、1000試合replayを確認した。

全機能有効・10万試合・seed42・意思決定上限512で、1/4スレッドの全統計とchecksumが一致した。

この10万試合では請求の合計実支払いと元の加算が一致したが、上限・資源不足がある局面での一般的な保証ではない。
旧14profileは従来のchecksum式を維持し、各10万試合で意思決定数・勝敗・draw・打ち切り・checksumが以前と一致した。
ベンチの速度出力は行動生成・合法性検証・遷移・統計・resetを含み、観測転送・モデル推論を含まない。

共通観測の新しい追加部分は[HP吸収v28](legacy-hp-absorption-profile.md)を参照。旧ABIの幅・行動形式は維持する。
