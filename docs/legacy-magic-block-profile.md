# 魔法遮断8種と通常の攻防 v19

`legacy-magic-block-subset-v19` は魔法遮断8種を追加する限定profile。
CLIの `magic-block` と `gw_*` は既存拡張も有効にし、195種・旧重み合計385で動く。
旧非公式エミュレーターを参考にしており、現行公式との完全一致は確認していない。

[処理順の調査](legacy-magic-block-rules.md)、[台帳・出典・hash](../data/legacy-magic-block-v1/README.md)、
[前段のMP武器profile](legacy-mana-weapon-profile.md)を参照。
既存18台帳を変更せず、追加8種を含むプール内で旧重みを正規化する。公式の配布率とは扱わない。

全8種とも無属性・MP費用0・保持化なし・攻撃付随状態なし。重み0の312/313/363は対象外。
3武器は通常の攻撃baseとして使え、55は他の武器へ追加ATK15として使える。

武器は捨てられず、5防具は捨てられる。

非MAGIC入力には5防具の通常DEFを使い、属性適合も通常どおり検証する。
counterにも通常防具として使えるが、魔法遮断の特殊baseとしては使えない。
3武器には通常DEFがなく、非MAGIC入力への普通防御の役割は持たせない。

## MAGICへの強制遮断

incomingがMAGICなら、8種を選ぶと必ず遮断が発火する。
`defend.base` に指定し、普通防具用 `slots` で遮断だけを省略する行動は拒否する。
複数の遮断品や他の一致する特殊品を、前置普通防具として消費することもできない。
特殊後の未使用suffixは、従来どおり意味的行動から省略する。旧XMLの選択列全体の再現は対象外。

基本4属性・光・闇の攻撃奇跡、命中済みの確率奇跡、回復216・所持金220も遮断する。
自己対象奇跡は即解決するため、遮断を選ぶ応答がない。
MP武器57はWEAPON、counterはPROTECTORなのでMAGIC遮断の対象外。
単にdamageかどうか、MPを使うかどうかで分類しない。

遮断品自身のDEFを差し引く前に特殊を発火し、奇跡本体のダメージ・回復・所持金増加・Glory等を適用しない。
前置防具の属性適合は不要。195で属性を消してもMAGIC由来は残り、遮断できる。
前置品の消費・配布予定・既に適用した病気等は残す。前置counterは消費されるが、反撃を予約しない。
Gloryの既存単枚制限では遮断品も1枚に数える。

攻撃者が支払ったMP、初使用の保持取得、元の配布予定、元の命中記録は取り消さない。
遮断者のMP支払や保持取得は発生せず、実際の消費枚数だけ配布予定を増やす。
反射のようにsource/targetを交換せず、新targetへの応答や命中抽選も行わない。

現在項目を終了し、既存の死亡確定・残queue・全項目後のowner tick/補充/勝敗順を使う。
Heavenに前置175を使って暫定HP0になった場合、回復奇跡を遮断してしまうと救済されず、その項目の終了時に死亡する。
通常の効果解決と、遮断による未適用を区別する。

## 状態と復元

`Config::magic_block` はデフォルトfalseで、他拡張を必須にはしない。
miraclesが無効なら新8種の通常武器・boost・防具の役割だけが使える。
保持奇跡の種類を増やさず、通常15種・防御2種の既存配列とmaskを維持する。

保持castの配布予定を追跡するretained_dealsは、本flagでも有効にする。
防御奇跡なしでは最大1、防御奇跡ありでは既存のMPに基づく保守上限20を維持する。
これにより、miracles+elements+counters+magic_blockだけの構成でも、満杯手札からの保持castを正しく復元し、
遮断後の余分な補充抽選を消費できる。無料化や追加MAGICはこのプールに含めない。
55の追加ATK15は既存最大値と同じなので、57の最大威力423・通常上限480・counter int64上限を変更しない。

公開イベントは `LastReaction{id=使用した遮断品, source=target=遮断者, reaction=block, from_ability=false}` とする。
これはイベント表現であり、元のsource/targetを交換する意味ではない。
遮断は項目を終了するため、未解決反射回数を増やさない。
StepResultの `magic_blocked` をtrueにし、`weapon_blocked`・`magic_reflected`・`any_reflected`とは区別する。

Snapshot共通versionは36。同じビルド・Config内のfixture用で、旧形式を自動移行する永続checkpointではない。
新8種の許可flag、blockという履歴種別、自己座席のイベント・非保持由来を検証する。
遮断履歴を反射や保持奇跡へ偽装したsnapshot、無効構成へ新IDを渡す復元・配布は拒否する。

## 観測とAPI

共通観測の追加部分と新しい順序付き行動は[HP吸収v28](legacy-hp-absorption-profile.md)を参照。旧ABIの幅・行動形式は維持する。

共通C++観測は1345次元、gw出力は先頭750次元。v19では末尾595特徴が0。gvは先頭732、gu以前も従来の幅を維持する。
既存のLastReactionのID・座席・block表現を使い、追加特徴は次のとおり。

| 位置 | 内容 |
| --- | --- |
| 732 | magic_block有効なら1 |
| 733〜748 | 自分の各手札が27/54/55/152/165/182/183/185なら1〜8を8で割る。その他0 |
| 749 | 最後の反応が新8種による魔法遮断なら1 |

749はreflectionやdefensive_miraclesが無効でも利用できる。既存354の汎用block特徴は、defensive_miracles有効時に維持する。
追加18特徴は旧profileでは0。相手の未使用手札・完全な保持数・未来の抽選値・乱数状態を含めない。
既存の威力等の正規化は1を超え得るので、全特徴が0〜1とは仮定しない。

新C ABI [magic_block_c_api.h](../include/godfield/magic_block_c_api.h) は `gw_*` version19。
既存defendのkind/base/slotsを使い、行動16byte・mask幅11・手札容量16を維持する。
候補はreaction_slotsへ入れ、MAGIC相手には一致する遮断品を普通防具候補から除外する。
maskは構成要素なので、prefixのcounter順序・Glory・特殊品の条件を `legal()` で検証する。

[Pythonラッパー](../python/magic_block_env.py)では `MagicBlockBatchEnv` を使う。

```sh
python3 python/magic_block_env.py
./build/godfield_legacy_bench 100000 1 42 magic-block
./build/godfield_legacy_bench 100000 4 42 magic-block
```

全active行の事前検証で原子的に拒否する。終了行は固定・報酬0で不正手を無視し、自動resetしない。
報酬は固定座席順。Pythonの返却バッファーは再使用するので、履歴へ保存する際はコピーする。
同一ハンドルの同時操作はしない。既存gl〜gkは6byte、gx/gy/gz/gu/gvは16byteで各観測幅も維持する。

有料の追加MAGIC・倍率/全体化・MP無料化、霧188・幻覚189、忘却・守護神・蘇生・死亡時効果・終末・複数人戦、
旧版Pythonとの動的差分実行と現行公式照合、学習器・学習済みモデルは未対応。衝突C01〜C05も残す。

## 検証結果（2026-10-31）

通常CTest58件、ASan/UBSan39件、19種類のPython suite計178テストが通過。
8種の通常役割と55の追加ATK、MAGIC時の強制遮断・slots opt-out拒否、全属性・命中済み％・回復/入金を検証した。
MP/保持の非返還、前置属性免除・195・病気・counter非予約、GloryとHeavenの暫定HP0、
57/COUNTERの型条件、最小構成の満杯保持cast/retained1/余分な抽選、復元・秘匿・旧ABI境界、1000試合replayも確認した。

全機能有効・10万試合・seed42・意思決定上限512で、1/4スレッドの全統計とchecksumが一致した。

このランダム方策のutility奇跡は自己対象を選ぶため、utility遮断は発生しなかった。対相手の回復/入金遮断はfixtureで検証した。
遮断を奇跡の効果解決・回復/所持金増加として数えず、攻撃者が既に支払ったMPと保持取得は使用実績として維持する。
prefixのDEFを有効なダメージ軽減へ数えたり、魔法反射・武器遮断に重ねて集計したりしない。

checksum v19は遮断回数・遮断神器・元奇跡payload・source/target/元owner・prefixの履歴を含める。
旧18profileのchecksum式を維持し、各10万試合で意思決定数・勝敗・draw・打ち切り・checksumが以前と一致した。
ASan/UBSanのベンチ1万試合でもReleaseの全統計とchecksumが一致した。
速度出力は行動生成・合法性検証・遷移・統計・resetを含み、観測転送・モデル推論を含まない。
